# Actor prepareBaseData: source-mirror resets vs. derived-field baseline resets

- Two visually-similar patterns existed in `ActorSystemModel.prepareBaseData()`/`CreatureSystemModel.prepareBaseData()`; only one is real:
  1. **Derived-field baseline reset** (KEEP): field is `persisted: false` (e.g. `derivedNumberField`, `CurrencyField({ persisted: false })`, `NullableCapNumberField({ persisted: false })`). Nothing else ever assigns it a starting value, so it must be explicitly reset to its baseline every `prepareBaseData()` pass before AE `'initial'`-phase changes layer on. Examples still in the codebase: `inventoryValue`, `encumbrance.carriedWeight/carryBonus/carryMultiplier/maxDexBonus/armorCheckPenalty`, `saves.fort/reflex/will`.
  2. **Source-mirror reset** (REMOVED, unproven): field is a normal persisted field (e.g. `requiredNumberField`), and code re-read `this._source.foo` back onto `this.foo` to "undo" AE drift from a prior `prepareData()` pass. Removed from `ActorSystemModel` (`speed.land/climb/swim/burrow/fly`) and `CreatureSystemModel` (`abilities.*.score`).

## Why the source-mirror pattern was removed
- Theoretical concern (confirmed via real Foundry v14 core source, `common/abstract/data.mjs` + `client/documents/abstract/client-document.mjs`): `DataModel#_initialize()` (which rebuilds every field fresh from `_source`) only runs via `reset()` or `_updateCommit()` — NOT on every `prepareData()` pass. `prepareData()` mutates the *same* persisted `system` instance repeatedly, so in theory a persisted field touched by an `'initial'`/`'final'`-phase AE change could drift/compound across passes if never reset.
- The one core mechanism found that forces a full rebuild: `Actor#_onCreateDescendantDocuments`/`_onUpdateDescendantDocuments`/`_onDeleteDescendantDocuments` (`client/documents/actor.mjs`, ~L701-745) call `this.reset()` ONLY when the changed descendant's parent `instanceof Item` (i.e. an AE nested inside an Item — a "grandchild" of the actor). It does NOT fire for AEs directly on the actor, or for an Item's own data fields changing (no AE involved) — e.g. the carried-item `inventoryValue` bug case.
- Despite this theoretical risk, the user empirically tested removing the `speed` source-mirror reset (comment/uncomment/re-test cycles live in Foundry) and found **no observable behavioral difference** — no stale/compounding downgrade values. Root cause of the discrepancy is unconfirmed (possibly this system's own Vue store layer causes more frequent full re-reads than raw Foundry-core analysis suggests; not investigated further per explicit instruction not to burn more effort here).

## If this "issue" resurfaces
- Symptom to watch for: a field driven by an `'initial'`- or `'final'`-phase AE change (especially a no-backing-AE live contribution like `PhysicalItem.getContributedActorChanges()`/`Creature._buildEncumberedChanges()`, or an AE living directly on the actor rather than nested in an item) shows stale, compounding, or otherwise incorrect values across repeated interactions (not just first load).
- Where to look: `ActorSystemModel.mts` / `CreatureSystemModel.mts` `prepareBaseData()` — check whether the drifting field needs a source-mirror reset re-added, or whether the real fix is elsewhere (e.g. store/sheet re-render forcing `reset()` more often than assumed).
- See also: `docs/architecture/actor-data-pipeline.md` for the full `prepareEmbeddedDocuments()`/`applyActiveEffects(phase)` call order.
